# Deploy rollback — design

**Status:** approved, ready for planning
**Date:** 2026-08-15
**Sub-project:** 4 of 4 in the platform observability & operations program
(1: logging kernel, 2: platform health & status, 3: error monitoring, 4: this)

---

## 0. What this sub-project is, and what it is not

The program item reads: *"roll back plan in case new deploys after prod break
the platform."*

The platform already has a documented rollback policy. `deploy/README.md`
("Upgrading an existing deployment") says:

> **Rolling back application code is `git checkout <old-sha> && rebuild`;
> rolling back a migration is not supported.** Migrations are forward-only.
> Restore the dump from step 1.

That policy is the right one and it is **confirmed** (§1). So this sub-project
is not a redesign. It is the work of making an asserted procedure into a
verified one — because every part of it that was measured turned out to be
either broken or unproven.

The same document says of its own upgrade sequence:

> ⚠ **UNVERIFIED as a sequence.**

This spec's job is to delete that warning honestly.

### 0.1 The invariant this sub-project must not break

Restoring a database is a tenancy event. `CLAUDE.md` invariant 5: *all data
access is tenant-scoped, enforced at the database layer via Row-Level
Security, not only in application code.* A restore that produces a database
with the tables but without the RLS policies would be a silent, total
tenant-isolation failure in exactly the moment nobody is looking closely —
the middle of an incident. §1.3 measures this specifically. It is the single
most important assertion in this document.

## 1. Measured ground truth

Everything in this section was **run**, not inferred, on 2026-08-15 against
throwaway databases and a purpose-built second Postgres cluster, all torn
down afterward. Where a claim is inferred rather than observed it says so.

### 1.1 Migrations: the downgrade path exits 0 and breaks the roll-forward

- 57 migrations under `backend/migrations/versions/`. All 57 define
  `downgrade()`. None is a `pass` stub.
- CI runs `alembic upgrade head` only. **The 57 `downgrade()` bodies have
  never executed anywhere** — not in CI, not in production.
- `alembic downgrade base` from head **succeeds, exit 0**, and drops all 125
  public tables. It does **not** drop the `job_status` enum type.

`0001_core_schema.py:160` creates that type implicitly:

```python
sa.Column('status', sa.Enum('queued', 'dispatched', 'running', 'succeeded',
                            'failed', 'expired', 'refused', name='job_status'),
          nullable=False),
```

and its autogenerated `downgrade()` drops the tables but never the type —
the classic Alembic autogenerate omission. The consequence is precisely the
rollback scenario, roll back then roll forward again:

```
sqlalchemy.exc.ProgrammingError: asyncpg.exceptions.DuplicateObjectError:
type "job_status" already exists
[SQL: CREATE TYPE job_status AS ENUM ('queued', 'dispatched', 'running',
 'succeeded', 'failed', 'expired', 'refused')]
```

`alembic upgrade head` exits 1. **The downgrade that caused it exited 0.**

Verified to be the sole blocker: `DROP TYPE job_status` by hand, then
`alembic upgrade head` → exit 0. With that one type handled,
`head → base → head` round-trips to a **byte-identical** `pg_dump
--schema-only` (9670 lines each), modulo §1.4.

> **How this was nearly missed, recorded because the lesson generalises.**
> The first check counted `information_schema.tables` after the downgrade,
> saw only `alembic_version`, and called the downgrade clean. Types are not
> tables. Only querying `pg_type WHERE typtype='e'` gave the answer. At head
> there is exactly **one** native enum type in `public`, which is why this
> defect is narrow — one type, one migration — rather than a 57-migration
> audit.

### 1.2 The restore works on this platform's real new-host path

> **CORRECTION.** An earlier revision of this section claimed the prescribed
> backup "cannot restore onto a new host". **That claim was wrong**, and it
> is recorded here rather than quietly deleted, because the way it was
> wrong is the same trap this document warns about twice elsewhere: the
> first measurement was taken against a *bare* `initdb` cluster, which is
> not how this platform builds a host. Measuring a proxy for the real thing
> gave a confident, wrong answer.

`deploy/README.md` step 1 and `deploy/GO-LIVE.md` §6 both prescribe:

```sh
docker compose exec -T postgres pg_dump -U its_admin -Fc itsuite > itsuite-$(date +%F).dump
```

That dump does emit **zero `CREATE ROLE` statements** while depending on
three cluster-level roles it cannot create. Against a bare cluster with none
of them present, `pg_restore` exits 1 with **266** errors — 130 `app_user`,
128 `its_admin`, 8 `portal_user` — though the 125 tables and their 122
FORCE-RLS settings still land, so the failure looks partial.

> **These numbers were re-measured on 2026-08-15 and they replace a
> previous "159".** That figure was the last surviving output of the
> retracted bare-cluster experiment: it counted only `TO <role>` occurrences,
> and it came from an Alembic-only source that had never been narrowed by
> `grant-app-privileges.sql`. A correctly-provisioned source carries more
> ACL entries and therefore more role references. Quoting an
> operator-facing number from a retracted experiment is how a retraction
> half-happens.

**But a new host on this platform is never a bare cluster.** `docker compose
up postgres` creates `its_admin` as the container's `POSTGRES_USER`, and
`deploy/postgres/init-app-user.sh` runs on first boot and creates `app_user`
and `portal_user`. All three roles therefore exist *before* any restore.
Replaying that first boot on a fresh cluster (`initdb -U its_admin`, then
the init script's role block) and restoring the prescribed dump:

```
roles present: 3
pg_restore EXIT=0   errors=0
tables: 125 | RLS policies: 133 | FORCE RLS: 122 | alembic_version: 0057
```

**Exit 0, zero errors.** The documented backup is sufficient for the
documented recovery path.

`pg_dumpall --roles-only` remains worth taking — it is what makes the dump
restorable into a target that is *not* built by this compose stack (a bare
cluster, a managed Postgres), where the 266-error failure is real. It is a
robustness addition, not a fix for a broken primary path, and §3.3 describes
it as such.

### 1.3 Privilege narrowing across a restore

> **THIRD CORRECTION — this section retracts its own SECOND correction.**
> An earlier revision said a restore re-widens `app_user`. A later revision
> retracted that as "measured, and still wrong". **The retraction was the
> thing that was wrong.** The restore *does* widen `app_user` on the path
> every document prescribes, and the correct behaviour was already written
> down in `docs/07-backup-restore.md` §3 ("Step 4 is not optional, and here
> is the proof"), with measured output, before this sub-project began.
> `CLAUDE.md` says a decision already in `docs/` wins; that document was
> never read, and this spec contradicted it for two revisions.
>
> Three errors, one shape: §1.2 measured an unrealistic **target**, the
> second correction an unrealistic **source**, and this one an unrealistic
> **target again** — a database created fresh by the test, which is not the
> database a restore actually lands in.

**The mechanism** (`docs/07-backup-restore.md` §3, confirmed here).
`init-app-user.sh` installs a standing rule on the `itsuite` database:

```sql
ALTER DEFAULT PRIVILEGES FOR ROLE its_admin IN SCHEMA public
    GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO app_user;
```

Tables that `pg_restore` creates in that database are created *by
`its_admin`*, so the rule fires and grants blanket rights. `pg_dump` records
each table's ACL as `GRANT` statements and **has no way to express "and
revoke what the default privileges would have added"** — so the dump's
narrower `GRANT SELECT` is additive, not corrective, and the result is the
union. Wide.

Measured, restoring a **correctly narrowed** source into a target that
carries the standing rule (`pg_default_acl` = 1), before the narrowing step:

```
pg_restore EXIT=0  errors=0
audit_events:     DELETE,INSERT,SELECT,UPDATE
permissions:      DELETE,INSERT,SELECT,UPDATE
role_permissions: DELETE,INSERT,SELECT,UPDATE
security_events:  DELETE,INSERT,SELECT,UPDATE
```

`permissions` and `role_permissions` carry **no trigger**. In that state
`app_user` can write the RBAC catalogue — invariant 6 — and the application
will not complain.

**So `grant-app-privileges.sql` (step 4 of the restore) is load-bearing on
the primary path, not a repair for legacy hosts.** `restore.sh` runs it
unconditionally and then asserts the end state.

**Why the second correction's measurement disagreed.** It restored into a
database the test had just created, where `pg_default_acl` is empty, so
nothing widened anything and the dump's narrow ACLs stood alone. That is
also why the `ITS_RESTORE_FORCE` path measures narrow: dropping the database
destroys the standing rule. Both are real behaviours of a database that is
*not* the one a first-boot restore targets. Confirmed by measuring
`pg_default_acl` directly: 1 on a compose-shaped `itsuite`, 0 after a
drop-and-recreate.

**A consequence worth stating, since it was checked rather than assumed.**
Dropping the database also destroys the standing rule that
`init-app-user.sh` set for *future* migrations. It is restored anyway,
because `pg_dump` dumps the `ALTER DEFAULT PRIVILEGES` statement itself and
`pg_restore` applies it after the tables: a table created after a forced
restore did receive `INSERT,SELECT,UPDATE,DELETE`. No manual step is needed.

**`audit_events` is backstopped; the RBAC catalogue is not.** The
`audit_events_immutable` trigger survives the restore and fires — a `DELETE`
failed with `ERROR: audit_events is append-only`. (The `UPDATE` path was not
exercised — untested, not proven.) `permissions` and `role_permissions` have
no equivalent.

### 1.4 Two things that are not rollback defects but affect the work

**Frozen timestamp defaults.** Three columns carry a *literal* timestamp as
their server default, baked at migration-run time rather than `now()`:
`credentials.created_at`, `enrollment_tokens.created_at`,
`org_vault_keys.created_at`. The default therefore differs between any two
databases by when migrations ran. This is a real defect and an **explicit
follow-up, out of scope here** — but the §3.4 schema-diff gate must normalise
it or it will produce a permanent false failure.

**`pg_dump`'s `\restrict` token.** Every dump carries a random
`\restrict`/`\unrestrict` nonce. The §3.4 gate must strip it.

### 1.5 Images: there is nothing to roll back to

`deploy/docker-compose.yml` builds all five application services (`api`,
`gateway`, `worker`, `migrate`, `web`) from `build:` with no `image:` tag.
Third-party services are properly pinned (`postgres:16`, `redis:7-alpine`,
`quay.io/keycloak/keycloak:26.0`, `quay.io/openbao/openbao:2.6.1`,
`minio/minio:RELEASE.2025-09-07T16-13-09Z`, `traefik:v3.6`,
`guacamole/guacd:1.5.5`).

So today's documented rollback — `git checkout <old-sha> && rebuild` —
*rebuilds* the previous release rather than *restoring* it. A rebuild is not
a rollback: base-image layers, apt/npm/pip resolution and build-time
downloads can all differ from what was originally shipped, so the artefact
you roll back to is not the artefact that was running.

## 2. Decisions

| # | Decision | Rationale |
|---|---|---|
| D1 | **Production database rollback is restore-from-backup.** Migrations stay forward-only; `alembic downgrade` is never a production procedure. | Already the documented policy. Accepts an RPO of the deploy window in exchange for never running 57 never-tested `downgrade()` bodies against live data. |
| D2 | **`downgrade()` remains a development and CI concern**, gated by §3.4 for migration correctness — not advertised as a rollback path. | The bodies exist and should be correct; pretending they are a production mechanism is what makes them dangerous. |
| D3 | **Migration `0001`'s `downgrade()` is edited in place.** | A `DROP TYPE` must happen at 0001's point in the chain, so a forward migration structurally cannot express the fix. The "never edit a shipped migration" rule protects the *upgrade* path — deployed databases have already run 0001's upgrade — and 0001's `downgrade()` has never executed anywhere. The exception is recorded in the migration itself. |
| D4 | **Application images are tagged with the short git SHA.** | Rollback becomes retagging, not rebuilding (§1.5). Unambiguous, automatic, no release ceremony. |
| D5 | **The backup procedure gains `pg_dumpall --roles-only`, and the restore procedure runs `grant-app-privileges.sql` as an ordered step and then verifies the end state.** | Neither is repairing a broken primary path — §1.2 and §1.3 both retract earlier claims that they were. The globals dump makes the backup restorable into a target this compose stack did not build; the narrowing step is free and idempotent for a correctly-provisioned source and repairs a never-narrowed one (`deploy/README.md`'s pre-`postgres-grants` deployments). The verification is there because this sub-project produced two confident, wrong findings about restore privileges: assert the end state, do not reason about it. |
| D6 | **Compose-level work is CI-verified, not locally verified**, and is labelled as such wherever it is claimed. | No Docker daemon is reachable from the development environment used for this spec. Claiming otherwise would repeat the `health.check` failure this project already paid for. |

## 3. The work

### 3.1 Fix `0001`'s downgrade (D3)

Append to `0001_core_schema.py::downgrade()`:

```python
    # The enum `job_status` is created IMPLICITLY by the `sa.Enum(...)` column
    # above, and Alembic's autogenerate does not emit its DROP. Without this
    # line `downgrade base` exits 0 and leaves the type behind, so the next
    # `upgrade head` dies with DuplicateObjectError -- i.e. the rollback
    # succeeds and the roll-FORWARD is what breaks.
    #
    # EDITING A SHIPPED MIGRATION, DELIBERATELY. CLAUDE.md says never to.
    # The rule protects the upgrade path: a deployed database has already run
    # this migration's upgrade(), so changing that would rewrite history.
    # This downgrade() has never executed anywhere -- CI has never run a
    # downgrade and production never will (spec D1) -- so correcting it
    # changes no deployed state. A forward migration cannot express the fix:
    # the DROP TYPE has to happen at THIS point in the chain.
    op.execute("DROP TYPE IF EXISTS job_status")
```

**Falsifier:** remove the line; §3.4's CI job must go red.

### 3.2 Versioned images (D4)

Each of the five application services gains an `image:` alongside its
`build:`:

```yaml
  api:
    image: itsuite/backend:${IT_SUITE_VERSION:-dev}
    build: ...
```

`api`, `gateway`, `worker` and `migrate` share the ONE name
`itsuite/backend` — they build the same context with the same Dockerfile and
differ only in `command`, so four names would build and store identical
bytes four times. `web` is its own artefact.

A `deploy/scripts/build-images.sh` resolves `IT_SUITE_VERSION` to
`git rev-parse --short HEAD`, builds, and records the value. Rollback sets
`IT_SUITE_VERSION` to the previous SHA and runs `docker compose up -d` — no
rebuild, no `git checkout`.

**Falsifier:** with `IT_SUITE_VERSION` set to a SHA never built and the
local image absent, `docker compose up -d` must fail loudly rather than
silently rebuilding from the working tree. *(CI-verified — D6.)*

### 3.3 Backup and restore procedure (D5)

The backup step becomes three commands, not two — both logical dumps plus
the globals:

```sh
pg_dumpall --roles-only -U postgres            > globals-$(date +%F).sql
pg_dump -U its_admin -Fc itsuite               > itsuite-$(date +%F).dump
pg_dump -U its_admin -Fc keycloak              > keycloak-$(date +%F).dump
```

and the restore is **ordered**: apply globals (only if the target lacks the
roles) → `CREATE DATABASE ... OWNER its_admin` → `pg_restore` →
`grant-app-privileges.sql`. `restore.sh` runs that SQL directly rather than
via `docker compose up postgres-grants`, so the ordering holds even when the
restore target is not this compose stack, and it then asserts the end state.

The runbook must state plainly what §1.2/§1.3 measured: a dump without
globals restores onto the *same* cluster fine and onto a bare cluster with 266
errors and zero application grants, and that the failure looks like success.

### 3.4 The migration-correctness CI gate (D2)

A new CI job — named for what it checks, `migration round-trip`, not
"rollback":

1. `alembic upgrade head`, `pg_dump --schema-only` → `ref.sql`
2. `alembic downgrade base`
3. assert **no** leftover objects: zero public tables besides
   `alembic_version`, and zero enum types in `public`. (Step 3 is the one
   that catches §1.1's class of defect. A downgrade's exit code does not.)
4. `alembic upgrade head`, `pg_dump --schema-only` → `roundtrip.sql`
5. normalise both (strip the `\restrict`/`\unrestrict` nonce and the §1.4
   frozen-timestamp defaults) and assert they are identical.

The job **fails on today's `main`** — that is the point, and it is how the
§3.1 fix is proven rather than asserted.

### 3.5 The runbook (D1)

`deploy/README.md` gains a rollback section giving the operator one ordered
path — retag to the previous SHA, and restore the pre-deploy dump only if
the schema moved — plus the honest statement of what is lost (writes since
the deploy) and what has and has not been exercised.

The "⚠ UNVERIFIED as a sequence" warning is replaced with a statement of
exactly which steps were verified, by what, and which remain unexercised.
It is not deleted merely because the section was rewritten.

## 5. Out of scope, recorded

- ~~**The frozen `created_at` defaults**~~ — **DONE**, migration `0058`.
  `credentials`, `enrollment_tokens` and `org_vault_keys` declared
  `server_default='now()'` with `now()` as a Python *string* rather than
  `sa.text('now()')`, so SQLAlchemy emitted `DEFAULT 'now()'::timestamptz`
  and Postgres froze it at DDL time. Measured before the fix, on a database
  migrated minutes earlier: all three defaulted to `2026-08-16
  02:04:30.663117+00`. After `0058`: all three are `now()`, and no frozen
  default remains anywhere in the schema.

  **The §3.4 CI filter was deleted in the same commit**, as its own comment
  demanded. The round-trip diff now compares those three lines like any
  other and was falsified against a planted regression:

  ```
  -    created_at timestamp with time zone DEFAULT now(),
  +    created_at timestamp with time zone DEFAULT '2026-08-16 02:06:15...'::timestamp with time zone,
  ```

  So the gate now catches the very defect it used to hide.

- **Automated pre-deploy backup.** This sub-project makes the manual
  procedure correct and verified; scheduling it is separate.
- **Keycloak realm rollback.** The `keycloak` database is dumped and
  restored by the same procedure, but its own config-rollback semantics are
  not analysed here.
- **Blue/green or zero-downtime deploys.** D1 accepts a maintenance window.
