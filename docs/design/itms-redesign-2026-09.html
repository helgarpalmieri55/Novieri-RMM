ITMS console · design direction · 7 September 2026

Sixty-five pages, eight archetypes

A redesign mockup for the ITMS operator console, produced with the design-taste-frontend skill. It is a direction to argue with, not a patch to apply.

Scope, stated first because the skill requires it

This brief is out of scope for the skill I was asked to use. design-taste-frontend §13 lists what it is not for, and ITMS is three items on that list at once: dense product UI and admin panels, data tables, and multi-step wizards. The skill's instruction in that case is to say so explicitly, name the right tool, and apply only the parts that transfer. That is what this document does.

The right tool, per the skill's own §2.A: an operations console of this density points at IBM Carbon (@carbon/react), which the skill picks out for “mature data-density patterns”. I have not adopted Carbon here, because that is a decision with a real migration cost attached. I have designed as if its density discipline applied, which is the transferable part.

What did transfer: layout discipline, the AI-tell bans, colour calibration, interactive-state completeness, the long-list rules, and the content-density rules. What did not: hero composition, scroll choreography, marquees, motion intensity, logo walls, and the whole landing-page vocabulary. An RMM console has no hero.

This does not drop into the codebase. docs/design/itms-prototype.html is the design authority, and tokens.test.ts (:root parity) plus base-styles.test.ts (selector-by-selector, whitespace-exact) enforce it. Every token below differs from the shipped set, so adopting any of it means changing the prototype first and the tests with it, deliberately.

Design variance
3
Near the skill's floor, against its 8 baseline. Operators build muscle memory across sixty-five pages; asymmetry that delights on a portfolio costs a second per page here, every page, every shift.
Motion intensity
2
A console that animates while somebody triages an outage is hostile. Motion is reserved for state change (a row arriving, a job finishing) and nothing else.
Visual density
8
Cockpit. The skill's own rule at this level: card containers banned, 1px lines separate data, mono for every number. The shipped console is card-heavy at roughly a 4.

Design read: operations console for on-call IT staff under time pressure, with a utilitarian data-density language, leaning toward Carbon-style discipline rather than any landing-page aesthetic.

The finding

The problem is not that the pages are ugly. It is that there are sixty-five of them.

I classified all 65 page components by structure: tables, tabs, stat grids, forms. They collapse into eight archetypes, and 28 of them are the same one. Those 28 are each built slightly differently: different filter placement, different empty states, different column ordering, different ideas about where a count goes.

So the highest-value redesign is not a new palette. It is eight components that 65 pages consume. The visual direction below matters, but it is the smaller half of the win.

Now

Colour is category

Tiles are blue for inventory, green for online, violet for tickets, red for alerts. The comment in DashboardPage.tsx states the rule outright: colour is category, weight is urgency. That is coherent, and it is the wrong axis for a screen somebody opens because a pager went off.

Proposed

Colour is severity, and nothing else

Four hues total: red needs a person, amber is degrading, green is fine, blue is in flight. Category is carried by position and label, which are free. The first tile answers the only question being asked at 02:00, and the left gutter repeats that answer on every row so the table is scannable without reading it.

Now

A count with no denominator

“286 devices.” True, and not actionable. The audit of 2026-08-20 caught this in its other direction, where a findings list read as a device count.

Proposed

Every number carries its own second line

7 is useless; “7 · 4 offline >24h, 3 certs expiring” is a work queue. The subtext is not decoration, it is the breakdown that makes the number a decision. Where nothing is measured the tile says so rather than printing a zero that reads as health.

What adopting it would actually cost

1. The prototype moves first

docs/design/itms-prototype.html is the authority. tokens.test.ts compares :root against it and base-styles.test.ts compares named selectors whitespace-exact. Any token here reaching the app without the prototype changing first turns both red. That ordering is a feature: it is what stopped the console drifting before.

2. Eight components, then 65 call sites

The archetypes are the deliverable, not the palette. Build RollupList, RegistryList, EntityDetail, SettingsPane, Journey, TileGrid, TabbedWorkspace, PortalPage; migrate the 28 archetype-A pages first, since they are where the inconsistency is.

3. The a11y pass is not optional here

docs/product.md §11 makes WCAG 2.2 AA binding and CI runs axe at five viewports. The severity palette above needs measuring, not asserting: amber on white is the one at risk, and #9a6100 was picked to clear 4.5:1 rather than because it looked right.

4. What I would not do

Adopt Carbon. The skill points there and it is the honest pointer, but swapping the component layer of a 65-page console for a third-party system is a quarter of work that buys density patterns you can get by writing eight components carefully. The pointer is worth recording; taking it is not.
