# Deploy Rollback Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make this platform's already-documented rollback policy — restore from backup, migrations forward-only — actually work and actually be verified, and give the operator an image to roll back *to*.

**Architecture:** Four independent pieces, in dependency order: correct migration `0001`'s downgrade; add a CI job that proves it (and fails without it); fix the backup procedure so a restore onto a new host succeeds; tag application images with the git SHA and write the runbook. Nothing here changes application code.

**Tech Stack:** Alembic, PostgreSQL 16, `pg_dump`/`pg_dumpall`/`pg_restore`, Docker Compose, GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-08-15-deploy-rollback-design.md` (commit `cd89b0d`). Read §1 before starting — every number in this plan comes from a measurement recorded there.

## Global Constraints

- **Migrations are forward-only.** The single exception in this plan is Task 1, which edits `0001_core_schema.py`'s `downgrade()` and must carry the comment specified there explaining why. No other shipped migration is edited, ever.
- **CLAUDE.md invariant 5 (tenancy).** Any change touching restore must preserve RLS. Measured post-restore, at head: 125 tables, **133** policies, **122** tables with `FORCE ROW LEVEL SECURITY`, `alembic_version` = `0057`. (An earlier revision of this line said 122 policies and "11 grants to `app_user`"; both were wrong — the grant count post-restore is in the hundreds, since it counts privilege rows across every table.)
- **Secrets never in code or git.** CI uses the existing throwaway-`.env` pattern (`.github/workflows/ci.yml`, the `deploy` job's "Throwaway .env" step). No real credential appears anywhere.
- **Claims must be measured, not asserted.** Where something cannot be verified in the environment it is written in, say so in the artefact itself. Specifically: **no Docker daemon is reachable from the development environment**, so Tasks 3 and 4's compose behaviour is CI-verified only and must be labelled that way.
- **Do not delete an honesty warning to tidy up.** `deploy/README.md`'s "⚠ UNVERIFIED as a sequence" may only be replaced by a statement of what *was* verified and what was not.
- Git: named paths only. Never `git add -A`, `git add .`, `git commit -a`, `git checkout .`, or `git stash`.

## Task 1: Correct `0001`'s downgrade

**Files:**
- Modify: `backend/migrations/versions/0001_core_schema.py` (end of `downgrade()`)

**Interfaces:**
- Consumes: nothing.
- Produces: a `downgrade base` that leaves no `public` enum types. Task 2's CI job asserts exactly this.

**Background:** `0001_core_schema.py:160` creates the `job_status` enum implicitly through `sa.Enum(..., name='job_status')`. Alembic's autogenerated `downgrade()` drops the tables but never the type. `alembic downgrade base` therefore **exits 0** while leaving the type behind, and the next `alembic upgrade head` dies with `DuplicateObjectError: type "job_status" already exists`. Verified as the sole blocker (spec §1.1).

- [ ] **Step 1: Reproduce the defect before fixing it.** With PostgreSQL running:

```bash
cd backend
sudo -u postgres psql -X -q -c "DROP DATABASE IF EXISTS rt_probe WITH (FORCE)"
sudo -u postgres psql -X -q -c "CREATE DATABASE rt_probe OWNER its_admin"
export U="postgresql+asyncpg://its_admin:its_admin_test@127.0.0.1:5432/rt_probe"
ITS_ALEMBIC_URL="$U" .venv/bin/alembic upgrade head
ITS_ALEMBIC_URL="$U" .venv/bin/alembic downgrade base
echo "downgrade exit: $?"
sudo -u postgres psql -X -A -t -d rt_probe -c \
  "SELECT t.typname FROM pg_type t JOIN pg_namespace n ON n.oid=t.typnamespace WHERE n.nspname='public' AND t.typtype='e'"
ITS_ALEMBIC_URL="$U" .venv/bin/alembic upgrade head
echo "re-upgrade exit: $?"
```

Expected: downgrade exit `0`; the type query prints `job_status`; re-upgrade exits `1` with `DuplicateObjectError`. **If the re-upgrade succeeds, stop and report** — the defect is not reproducing and the fix would be unfalsifiable.

- [ ] **Step 2: Apply the fix.** Append to the end of `downgrade()` in `backend/migrations/versions/0001_core_schema.py`, after `op.drop_table('organizations')` and before the `# ### end Alembic commands ###` marker:

```python
    # The enum `job_status` is created IMPLICITLY by the `sa.Enum(...)` column
    # on `jobs.status` above, and Alembic's autogenerate does not emit its
    # DROP. Without this line `downgrade base` exits 0 and leaves the type
    # behind, so the next `upgrade head` dies with DuplicateObjectError --
    # the rollback succeeds and the roll-FORWARD is what breaks.
    #
    # EDITING A SHIPPED MIGRATION, DELIBERATELY. CLAUDE.md says never to.
    # The rule protects the UPGRADE path: a deployed database has already run
    # this migration's upgrade(), so changing that would rewrite history.
    # This downgrade() has never executed anywhere -- CI has never run a
    # downgrade, and production never will (rollback is restore-from-backup,
    # spec D1) -- so correcting it changes no deployed state. A forward
    # migration cannot express the fix: the DROP TYPE has to happen at THIS
    # point in the chain, when the table that uses the type goes away.
    op.execute("DROP TYPE IF EXISTS job_status")
```

- [ ] **Step 3: Verify the round-trip now closes.** Re-run Step 1's block. Expected: downgrade exit `0`, the type query prints **nothing**, re-upgrade exits `0`.

- [ ] **Step 4: Verify the schema is unchanged by the round-trip.**

```bash
sudo -u postgres psql -X -q -c "DROP DATABASE IF EXISTS rt_ref WITH (FORCE)"
sudo -u postgres psql -X -q -c "CREATE DATABASE rt_ref OWNER its_admin"
ITS_ALEMBIC_URL="postgresql+asyncpg://its_admin:its_admin_test@127.0.0.1:5432/rt_ref" \
  .venv/bin/alembic upgrade head
sudo -u postgres pg_dump --schema-only --no-owner --no-privileges -d rt_ref    > /tmp/ref.sql
sudo -u postgres pg_dump --schema-only --no-owner --no-privileges -d rt_probe  > /tmp/rt.sql
diff <(grep -v '^\\\(un\)\?restrict' /tmp/ref.sql | grep -v "created_at timestamp with time zone DEFAULT '") \
     <(grep -v '^\\\(un\)\?restrict' /tmp/rt.sql  | grep -v "created_at timestamp with time zone DEFAULT '") \
  && echo IDENTICAL
```

Expected: `IDENTICAL`. The two `grep -v` filters remove `pg_dump`'s random `\restrict` nonce and the three frozen-timestamp defaults (spec §1.4) — both differ between any two databases for reasons unrelated to this change.

- [ ] **Step 5: Clean up.** `sudo -u postgres psql -X -q -c "DROP DATABASE IF EXISTS rt_probe WITH (FORCE)"` and the same for `rt_ref`.

- [ ] **Step 6: Commit.**

```bash
git add backend/migrations/versions/0001_core_schema.py
git commit -m "fix(migrations): drop the job_status enum in 0001's downgrade

Paste the before/after exit codes and the type-name query output from
Steps 1 and 3 into the commit body."
```

## Task 2: The migration round-trip CI job

**Files:**
- Modify: `.github/workflows/ci.yml` (new top-level job, after `backend`)

**Interfaces:**
- Consumes: Task 1's fix.
- Produces: a CI gate named `migration round-trip`.

**Background:** CI runs `alembic upgrade head` only; the 57 `downgrade()` bodies have never executed anywhere (spec §1.1). This job is a **migration-correctness** check, not a production rollback mechanism (spec D2) — name it and comment it as such, because mislabelling it is how a never-tested path acquires false credibility.

Model the job on the existing `backend` job (lines 14–70): it starts the runner's preinstalled PostgreSQL and installs into `backend/.venv`, which is what `alembic` needs. Do **not** model it on the `deploy` job — that one boots compose and its RLS assertions need a database this job would disturb.

- [ ] **Step 1: Add the job.** Insert after the `backend` job:

```yaml
  migrations:
    # MIGRATION CORRECTNESS, NOT A ROLLBACK MECHANISM. Production rollback is
    # restore-from-backup (docs/superpowers/specs/2026-08-15-deploy-rollback-design.md
    # D1); `alembic downgrade` is never run against live data. This job exists
    # because the 57 downgrade() bodies had never executed ANYWHERE -- CI ran
    # `upgrade head` and nothing else -- which is how 0001 came to leave the
    # job_status enum behind while exiting 0, breaking the next upgrade.
    name: migration round-trip (upgrade · downgrade · upgrade)
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: backend
    steps:
      - uses: actions/checkout@v4

      - name: Start PostgreSQL
        run: |
          sudo systemctl start postgresql
          for i in $(seq 1 30); do
            if sudo -u postgres psql -tAc 'SELECT 1' >/dev/null 2>&1; then
              echo "postgres ready"; exit 0
            fi
            sleep 1
          done
          echo "postgres did not become ready" >&2
          exit 1

      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"

      - name: Install backend
        run: |
          python -m venv .venv
          .venv/bin/pip install --upgrade pip
          .venv/bin/pip install -e '.[dev]'

      - name: Create roles and databases
        run: |
          sudo -u postgres psql -X -q -c \
            "DO \$\$ BEGIN IF NOT EXISTS (SELECT FROM pg_roles WHERE rolname='its_admin') THEN
               CREATE ROLE its_admin LOGIN PASSWORD 'its_admin_test' NOSUPERUSER CREATEDB CREATEROLE;
             END IF; END \$\$;"
          sudo -u postgres psql -X -q -c "ALTER ROLE its_admin BYPASSRLS"
          sudo -u postgres psql -X -q -c "CREATE DATABASE rt_ref   OWNER its_admin"
          sudo -u postgres psql -X -q -c "CREATE DATABASE rt_probe OWNER its_admin"

      - name: Reference schema (straight upgrade head)
        run: |
          ITS_ALEMBIC_URL="postgresql+asyncpg://its_admin:its_admin_test@127.0.0.1:5432/rt_ref" \
            .venv/bin/alembic upgrade head
          sudo -u postgres pg_dump --schema-only --no-owner --no-privileges -d rt_ref > /tmp/ref.sql

      - name: upgrade head, then downgrade base
        run: |
          ITS_ALEMBIC_URL="postgresql+asyncpg://its_admin:its_admin_test@127.0.0.1:5432/rt_probe" \
            .venv/bin/alembic upgrade head
          ITS_ALEMBIC_URL="postgresql+asyncpg://its_admin:its_admin_test@127.0.0.1:5432/rt_probe" \
            .venv/bin/alembic downgrade base

      - name: assert the downgrade left NOTHING behind
        # THE STEP THAT CATCHES THE REAL DEFECT CLASS. A downgrade's exit code
        # does not: `downgrade base` exited 0 while orphaning an enum type,
        # because dropping tables is all autogenerate emits. Types are not
        # tables, so counting tables alone would pass here too.
        run: |
          tables=$(sudo -u postgres psql -X -A -t -d rt_probe -c \
            "SELECT count(*) FROM information_schema.tables
             WHERE table_schema='public' AND table_name <> 'alembic_version'")
          enums=$(sudo -u postgres psql -X -A -t -d rt_probe -c \
            "SELECT count(*) FROM pg_type t JOIN pg_namespace n ON n.oid=t.typnamespace
             WHERE n.nspname='public' AND t.typtype='e'")
          echo "leftover tables: $tables, leftover enum types: $enums"
          if [ "$tables" != "0" ] || [ "$enums" != "0" ]; then
            echo "::error::downgrade base left objects behind"
            sudo -u postgres psql -X -d rt_probe -c \
              "SELECT t.typname FROM pg_type t JOIN pg_namespace n ON n.oid=t.typnamespace
               WHERE n.nspname='public' AND t.typtype='e'"
            exit 1
          fi

      - name: upgrade head again, and diff the schema
        run: |
          ITS_ALEMBIC_URL="postgresql+asyncpg://its_admin:its_admin_test@127.0.0.1:5432/rt_probe" \
            .venv/bin/alembic upgrade head
          sudo -u postgres pg_dump --schema-only --no-owner --no-privileges -d rt_probe > /tmp/rt.sql
          # Normalise two things that differ between ANY two databases for
          # reasons unrelated to migrations: pg_dump's random \restrict nonce,
          # and three created_at defaults frozen to migration-run wall-clock
          # time (spec §1.4 -- a real defect, tracked separately).
          norm() { grep -v '^\\\(un\)\?restrict' "$1" \
                   | grep -v "created_at timestamp with time zone DEFAULT '"; }
          norm /tmp/ref.sql > /tmp/ref.norm
          norm /tmp/rt.sql  > /tmp/rt.norm
          diff -u /tmp/ref.norm /tmp/rt.norm
```

- [ ] **Step 2: Prove the job fails without Task 1's fix.** On a scratch branch, revert only the `op.execute("DROP TYPE IF EXISTS job_status")` line and run the job's commands locally (Task 1 Step 1's block plus the leftover-objects query). Expected: the "assert the downgrade left NOTHING behind" logic reports `leftover enum types: 1` and exits 1. Restore the line by **editing**, never `git checkout`. Confirm `git diff` is empty afterward. Record the observed output in the commit body.

- [ ] **Step 3: Commit.**

```bash
git add .github/workflows/ci.yml
git commit -m "ci: add the migration round-trip gate

Include Step 2's observed failure output in the body."
```

## Task 3: Backup and restore that works on a new host

**Files:**
- Modify: `deploy/GO-LIVE.md` (§6, the backup block)
- Modify: `deploy/README.md` ("Upgrading an existing deployment", step 1)
- Create: `deploy/scripts/backup.sh`
- Create: `deploy/scripts/restore.sh`

**Interfaces:**
- Consumes: nothing.
- Produces: `backup.sh` writing three artefacts to a directory; `restore.sh` consuming that directory in the correct order. Task 4's runbook calls both by name.

**Background — the measurement that drives this (spec §1.2/§1.3). Read the CORRECTION note at the top of spec §1.2 first: an earlier revision of this plan asserted the restore was broken, and it is not.**

On this platform's real new-host path — `docker compose up postgres` creates `its_admin` as `POSTGRES_USER` and `init-app-user.sh` creates `app_user` and `portal_user` — the prescribed dump restores with **exit 0, zero errors**, 125 tables, 133 policies, 122 FORCE RLS, `alembic_version` = `0057`. Against a *bare* cluster with no roles it is exit 1 with ~266 errors (re-measured; an earlier "159" came from the retracted experiment and an un-narrowed source — and an independent re-run counted 267, so treat the exact figure as environment-sensitive), which is why `pg_dumpall --roles-only` is still worth taking; that is a robustness addition for non-compose targets, not a fix for a broken primary path. Do not write it up as one.

**Read spec §1.3's THIRD CORRECTION, and read `docs/07-backup-restore.md` §3 before either.** This plan twice told its implementer the wrong thing about restore privileges. The settled, measured answer:

**The restore DOES widen `app_user`, and `grant-app-privileges.sql` is load-bearing on the primary path.** `init-app-user.sh` installs a standing `ALTER DEFAULT PRIVILEGES` on the `itsuite` database; tables `pg_restore` creates there are created *by* `its_admin`, so the rule fires and grants blanket rights. `pg_dump` records ACLs as `GRANT` statements and cannot express the compensating `REVOKE`, so the dump's narrower grant is **additive** and the result is the union. Measured, restoring a correctly narrowed source into a target carrying the rule, before the narrowing step: `audit_events`, `permissions`, `role_permissions` and `security_events` all came back `DELETE,INSERT,SELECT,UPDATE`. `permissions` and `role_permissions` have no trigger backstop.

**Do not write this up as "free and idempotent."** `deploy/scripts/restore.sh`'s header forbids that phrasing in capitals, for this reason. An earlier revision of this plan measured the restore coming back narrow — that measurement was taken against a database the test had just created, where `pg_default_acl` is empty. The `ITS_RESTORE_FORCE` path measures narrow for the same reason (dropping the database destroys the rule), and that is a genuine difference worth stating, not a general truth.

`docs/07-backup-restore.md` §3 ("Step 4 is not optional, and here is the proof") said all of this before this sub-project began, and it is authoritative under `CLAUDE.md`. Where this plan and that document disagree, that document wins.

- [ ] **Step 1: Write `deploy/scripts/backup.sh`.** Three artefacts into a dated directory: `pg_dumpall --roles-only`, then `-Fc` dumps of `itsuite` and `keycloak`. Comment the globals dump accurately — it is what makes the dump restorable into a target this compose stack did not build, where a role-less restore is exit 1 with ~266 role-does-not-exist errors. Do not claim it fixes the compose path; that path already works. Fail loudly if any of the three artefacts is empty or absent afterward.

- [ ] **Step 2: Write `deploy/scripts/restore.sh`.** Strict ordering, because the order is the fix: apply globals → `CREATE DATABASE ... OWNER its_admin` → `pg_restore` → apply `grant-app-privileges.sql` directly (not via `docker compose up postgres-grants`, so the ordering holds on a non-compose target) and then assert the end state. Refuse to run if the globals file is missing rather than proceeding to a restore that will half-succeed.

- [ ] **Step 3: Verify both scripts against a real second cluster, built the way compose builds one.** Not against the live cluster, and **not** against a bare `initdb` — a bare cluster is the proxy that produced this plan's retracted claim. Build it as the platform does: `initdb -U its_admin`, then replay `init-app-user.sh`'s role block (`app_user`, `portal_user`, the `GRANT CONNECT`s, and the `ALTER DEFAULT PRIVILEGES FOR ROLE its_admin`). Then back up from the working database, restore, and assert:

```bash
# after restore, against the FRESH cluster
pg_restore exit 0, ZERO "pg_restore: error" lines
tables=125  force_rls=122  alembic_version=<head>
# and the finding this task exists for:
app_user grants on audit_events / permissions / security_events == DELETE,INSERT,SELECT,UPDATE
# then run grant-app-privileges.sql and assert they are narrowed:
audit_events -> no UPDATE/DELETE;  permissions -> SELECT only
```

The post-`postgres-grants` assertion is the load-bearing one: it is what proves the ordered procedure actually re-narrows the role, rather than the runbook merely saying so. Prove it is not vacuous by checking the wide privileges are genuinely present *before* the script runs — a narrowing test that never saw the wide state proves nothing. Tear the cluster down.

- [ ] **Step 4: Update `deploy/GO-LIVE.md` §6 and `deploy/README.md` step 1** to call `backup.sh`, and state what §1.3 measured: without the narrowing step `app_user` comes back holding `DELETE,INSERT,SELECT,UPDATE` on `audit_events`, `permissions`, `role_permissions` and `security_events`, and `permissions`/`role_permissions` have no trigger backstop — so the application role could rewrite the RBAC catalogue. `grant-app-privileges.sql` is therefore mandatory on every restore, not repair for legacy hosts.

  Also state that `globals.sql` carries the roles' SCRAM password hashes (`docs/07-backup-restore.md` §2.1: *"It is a secret. Encrypt it, or skip it entirely."*), since `backup.sh` now writes it unconditionally.

  **Two earlier revisions of this step said the opposite in different ways.** Neither survived measurement against the target a restore actually lands in. If you find yourself writing "the restore comes back narrow", check `pg_default_acl` on your test target first — if it is empty, your target is not a compose-built database.

- [ ] **Step 5: Verify the scripts using the command line the DOCS give**, not a convenient one. Run them from `deploy/` as `./scripts/backup.sh` and `./scripts/restore.sh`, with no environment overrides beyond `ITS_RESTORE_FORCE`. Verifying a different invocation than the one that ships is how a path-resolution bug survived a hand-verified "end to end" claim: the documented invocation dropped and restored the database and only then died, before the narrowing ever ran.

- [ ] **Step 6: Commit,** putting Step 3's measured outcomes in the body.

## Task 4: Versioned images and the rollback runbook

**Files:**
- Modify: `deploy/docker-compose.yml` (five app services)
- Create: `deploy/scripts/build-images.sh`
- Modify: `deploy/README.md` (new rollback section; the "⚠ UNVERIFIED" paragraph)
- Modify: `.github/workflows/ci.yml` (the existing `deploy` job)

**Interfaces:**
- Consumes: Task 3's `backup.sh` / `restore.sh`.
- Produces: `IT_SUITE_VERSION` as the rollback control.

**Background:** all five app services (`api`, `gateway`, `worker`, `migrate`, `web`) build from `build:` with no tag, so today's documented rollback — `git checkout <old-sha> && rebuild` — rebuilds the previous release rather than restoring it. Base layers and dependency resolution can differ, so the artefact rolled back to is not the artefact that shipped (spec §1.5).

- [ ] **Step 1: Add `image:` alongside `build:`** on each of the five services: `image: itsuite/<service>:${IT_SUITE_VERSION:-dev}`. Leave third-party pins untouched — they are already correct.

- [ ] **Step 2: Write `deploy/scripts/build-images.sh`** resolving `IT_SUITE_VERSION` to `git rev-parse --short HEAD`, building all five, and printing the tag it produced.

- [ ] **Step 3: Extend the existing `deploy` CI job** with a step asserting the tag is honoured: build at the current SHA, then run `docker compose config` with `IT_SUITE_VERSION` set to a SHA that was never built and assert the resolved image reference contains that SHA. Compose must not silently fall back to rebuilding from the working tree.

- [ ] **Step 4: Write the rollback section in `deploy/README.md`.** One ordered path, and **the order is the whole thing**: decide (compare the live `alembic_version` against the one `backup.sh` recorded beside the dumps) → **stop the app tier** → restore with `restore.sh` **only if** the schema moved → confirm the revision → retag → `docker compose up -d`.

  Retagging and starting *before* restoring — which an earlier revision of this step prescribed — runs the old image's `alembic upgrade head` against the *new* schema. It fails with "Can't locate revision identified by …", and `api`/`gateway`/`worker` never start because they depend on `migrate` completing. It breaks precisely when the schema moved, i.e. in the only case step 3 exists for.

  State what is lost — every write since the backup, **including audit history**, since `audit_events` is hash-chained and rewinds with it — and that `alembic downgrade` is not a production procedure and why. Also state that the images roll back but `docker-compose.yml` and `.env` do not, and that `docker system prune` destroys rollback targets.

- [ ] **Step 5: Replace the "⚠ UNVERIFIED as a sequence" paragraph** with what is now actually true: which steps are exercised by CI (`deploy` job: first boot, `upgrade head`, grants idempotency, RLS narrowing; `migrations` job: the round-trip), which were verified by hand and how (Task 3 Step 3's fresh-cluster restore), and which remain unexercised (a real `git pull`-over-an-older-release upgrade; compose image-tag rollback on a live host). **Do not delete the warning** — narrow it to what is still unproven, and mark the compose-level claims CI-verified rather than field-verified (spec D6).

- [ ] **Step 6: Commit.**
